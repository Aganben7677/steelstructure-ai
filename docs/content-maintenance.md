# Content Maintenance

## Public Site Structure

- Opportunity research: Daily Brief -> Projects -> EPC -> Supply Chain.
- Tender preparation: Knowledge -> review topics -> Resources -> working templates.
- Platform context: Field Notes, About and Contact.

## Knowledge Notes

Edit the bilingual records in `js/knowledge-notes.js`. Each record has a stable
anchor ID, title, summary, review points, working documents and a clarification
example. Keep IDs stable so existing links continue working. Update the content
edition in `js/i18n.js` when editorial changes are published.

These are editorial review prompts. Do not invent code requirements, acceptance
limits or material equivalences. Add technical claims only after checking the
project context and primary references.

## Resources

`resources.html` links to three blank CSV registers in `assets/templates/`.
They use UTF-8 with a BOM for Chinese field labels in spreadsheet applications.
Publish blank templates only; completed client or project registers belong outside
this public repository. Official standards links point to publisher catalogs.

## Briefs

Keep the existing `scripts/publish-brief.js` workflow. The homepage preview reads
`data/briefs/latest.json`, taking the first three signals and their original source
links. The Daily Brief page opens the full sourced issue and its archive while
retaining existing historical summaries. The homepage displays the actual issue date, and labels issues older than seven days
as historical. If the feed cannot load, the explicitly dated archive preview stays
visible. No news is automatically researched or generated by the website.

When changing the fallback preview in `index.html`, update its date and both
languages in the shared translation catalog together. Never present an older issue as
today's news. Record source dates separately from editorial publication dates.

## Release Checks

1. Check local links, scripts, template encoding and matching translation keys.
2. Preview Home, Knowledge and Resources in English and Chinese on desktop/mobile.
3. Check topic search, topic anchors, CSV downloads and dated brief fallback.
4. Commit and push to the existing GitHub Pages repository.
5. Confirm the Pages build and live pages before reporting the release complete.

`scripts/check-content.cjs` runs the browser checks with Playwright. Set
`CHROME_PATH` to an installed Chrome executable and make the Playwright package
available through Node's module resolution. It starts a temporary local server,
checks both languages at four widths, and closes the browser and server on exit.
